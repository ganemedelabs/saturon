Saturon parses colors with a full CSS grammar, which is usually the slow, careful way to build a color library. This page measures what that costs in practice, compares it to other popular color libraries, and explains how to reproduce every number.

On this workload, culori is the fastest library at parsing function-style strings and hex colors, at conversion, and at stringifying. Saturon is the fastest at parsing named colors. Saturon is faster than colorjs.io on every task, and faster than chroma-js at all three kinds of parsing and at stringifying. It is slower than culori everywhere except named colors, and slower than chroma-js at conversion.

<Callout type="warn" title="Read this before quoting the numbers">
    Microbenchmarks measure small, isolated operations. They are useful for comparing libraries on the same task, but
    they don't predict the speed of your application. Treat the results as one input, not a verdict. See
    [Limitations](#limitations).
</Callout>

## What is measured

Every library runs the same tasks over the same inputs. Timing is done with [mitata](https://github.com/evanwashere/mitata).

| Task               | What the benchmark does                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------ |
| Parsing (function) | Parses a function-style CSS color string, such as `lch(...)`, and reads back numbers from the result   |
| Parsing (hex)      | Parses a hex color string and reads back numbers from the result                                       |
| Parsing (named)    | Parses a named color, such as `rebeccapurple`, and reads back numbers from the result                  |
| Conversion         | Builds a color from a model name and coordinates, then converts it to a randomly chosen target model   |
| Stringify          | Builds a color from a model name and coordinates, then serializes it as a CSS string in the same model |

The conversion and stringify tasks include building the color object from its coordinates, because that is part of each library's normal call sequence.

### Inputs

- **Size:** 10,000 inputs per task. The parsing inputs and the conversion/stringify inputs are generated separately.
- **Models:** random colors from `Color.random()`, kept only if the model is `rgb`, `hsl`, `lab`, or `lch` and every coordinate is a finite number.
- **Function-style parsing inputs:** each random color serialized with `toString({ precision: 1, units: true })`, for example `lch(31% 104.7 271.7deg)`.
- **Hex parsing inputs:** each random color converted with `to("hex-color")`, for example `#1f7ac4`.
- **Named parsing inputs:** color names taken from Saturon's `namedColors` table, for example `rebeccapurple`.
- **Conversion and stringify inputs:** a model name and coordinates, in Saturon's coordinate ranges (`rgb` channels 0-255, `hsl` saturation and lightness 0-100).
- **Conversion targets:** one of `rgb`, `hsl`, `lab`, or `lch` per input, chosen with a fixed-seed generator (seed 42). Because targets are independent of the source model, about a quarter of the conversions are to the model the color already has.
- **Fresh data every run:** the random colors are not seeded, so each run uses a different dataset. Only the target sequence is fixed.

### API calls used

| Library         | Parse                    | Convert                                    | Stringify                             |
| --------------- | ------------------------ | ------------------------------------------ | ------------------------------------- |
| Saturon (class) | `Color.from(str).coords` | `new Color(model, coords).in(target)`      | `new Color(model, coords).toString()` |
| Saturon (utils) | `parse(str).coords`      | `convert({ model, coords }, target)`       | `format({ model, coords }, model)`    |
| chroma-js       | `chroma(str).rgba()`     | `chroma(coords, model)[target]()`          | `chroma(coords, model).css(model)`    |
| colorjs.io      | `new Color(str).coords`  | `new Color(space, coords).to(targetSpace)` | `new Color(space, coords).toString()` |
| culori          | `parse(str)`             | `converter(target)(colorObject)`           | `formatCss(colorObject)`              |

- The parse column is used for all three parsing tasks. Only the input strings change.
- "Saturon (class)" uses the [`Color`](/docs/api/color-class) class. "Saturon (utils)" uses the tree-shakable functions [`parse`](/docs/api/subpaths/parse), [`convert`](/docs/api/subpaths/convert), and [`format`](/docs/api/subpaths/format).
- For colorjs.io, `rgb` maps to its `srgb` space; `hsl`, `lab`, and `lch` map to the space of the same name.
- For culori, the four converters are created once before timing. The color object (`mode` plus the three channels) is built inside the timed loop, like the other libraries' constructors.
- Each library serializes with its own serializer, so the output strings differ in syntax and precision between libraries.

## Methodology

- All libraries receive identical input strings or identical `model` and `coords` values. Dataset generation, the JSON round trip of the dataset, and culori's converter creation happen before any timing.
- Parsing returns each library's native numbers: coordinates in the parsed color's own model for Saturon and colorjs.io, sRGB values for chroma-js, and a color object for culori. The conversion and stringify tasks produce each library's own result type.
- Each timed function keeps the last result of its loop and passes it to mitata's `do_not_optimize`, so the engine can't discard the work as dead code.
- Mitata warms up each benchmark before it measures. Saturon keeps a global cache of its conversion graph, conversion paths, component ranges, and model layouts, and that cache is warm during the timed runs. It doesn't cache parse results between calls, so repeating the same input strings doesn't speed up Saturon's parsing. The other libraries were not audited for internal caching.
- The script runs as `node bench.mjs`, with no extra flags.
- The versions in the tables are the ones locked in `pnpm-lock.yaml`. mitata is `1.0.34`.
- Numbers come from one run on the hardware listed above. The min-max columns show the spread across mitata's samples within that run. Absolute times will differ on your machine; compare the relative numbers.

## Limitations

- Libraries don't do the same amount of work. Saturon validates input against the full CSS color grammar, and it accepts syntax that some of these libraries don't parse at all. A faster library that accepts less is not doing the same job. This benchmark parses only function-style `rgb`, `hsl`, `lab`, and `lch` strings, hex colors, and named colors, so Saturon's wider syntax support isn't measured here. For how each library handles the full grammar, see [Conformance](/docs/conformance).
- The function-style parsing strings are produced by Saturon's own serializer, and the conversion inputs use Saturon's coordinate ranges without rescaling per library. Some libraries expect other ranges for the same model (for example, culori expects `rgb` channels from 0 to 1), so they receive values outside their usual range.
- The benchmark measures time only. It doesn't compare the values each library returns.
- Each timed operation is tiny and repeated many times, which favors code that the JIT compiler optimizes well. Real applications also pay for allocation, bundling, and cold starts. This matters most for named colors, where a single operation takes under a microsecond for the fastest libraries.
- Conversion and stringify use only `rgb`, `hsl`, `lab`, and `lch`. Other models, the `color()` function, and newer syntax such as `color-mix()` and relative colors are not measured.
- Mixing, interpolation, gamut mapping, contrast, and color difference are not measured. Memory use isn't compared either, although mitata prints heap figures in its raw output. For bundle size, see [Tree Shakability & Bundle Size](/docs/guides/tree-shakability).
- All numbers come from a single Windows machine on one Node.js version.
- Every library here changes over time. These numbers describe the versions listed on the date listed.

## Reproduce the results

From the repository root:

```bash
pnpm install
pnpm bench
```

The benchmark lives in [`apps/benchmarks`](https://github.com/ganemedelabs/saturon/tree/main/apps/benchmarks). It generates its dataset in memory on every run, so no data files are needed, and your numbers will vary slightly from the ones above.
